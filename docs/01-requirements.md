## 1. 产品定义

一句话：以项目目录为一级维度、把 agent 工作过程变成团队共享 thread 的本地优先工作台。

展开说三件事：

1. **共享单位是 thread**，不是仓库、不是聊天窗口。一条 thread 绑定一个隔离工作区、一个 agent 会话和一组未提交变更。
2. **展示单位是 project**。一个 project 对应本地一个目录（通常是 git 仓库），project 下挂多条 thread。打开产品先看到 project，再看到这个项目里正在发生什么。
3. **agent 是外部进程**。Claude Code、Codex、opencode、pi 由用户自己安装、自己登录、自己付费。产品不建设模型能力，只负责编排、展示、协作和审批。

## 2. 问题与定位

现有 agent 的工作过程默认是单人的、被困在终端里的：

- 队友看不到你在让 agent 做什么，也无法在你离开时接手。
- 对话在 agent 自己的会话文件里，代码变更是未提交的本地改动，两者对不上。
- 换一个 agent，历史、工具调用形态、审批方式全部重来。
- 想让人评审，只能先 commit、开 PR，把中间过程丢掉。

Delta 的解法是自建 harness 和同步层。本产品的解法相反：复用现有 agent，把「共享、过程留痕、审批、评审」做在 agent 之外的产品层。

因此产品的护城河不在 agent 能力，而在协作体验和过程数据。

## 3. 目标用户与场景

目标用户：2 到 10 人的小团队，成员已经在用 Claude Code、Codex、opencode 或 pi，并且各自有订阅或 API 额度。

三个核心场景：

| 场景 | 描述 | 成功标准 |
| --- | --- | --- |
| 结对 | 一个人在跑 agent，另一个人实时看过程，随时补充约束或接手 | 观看者不需要对方截图或转发，看到的就是同一份消息和 diff |
| 交接 | 跑长任务的人下班或离开，队友在原 thread 上继续 | 接手后上下文不丢，agent 不需要重新解释任务 |
| 评审 | 变更还没提交，先让队友在 diff 上留意见 | 意见挂在具体行上，作者能在同一 thread 里回复和处理 |

次要场景：给外部贡献者或客户开一条只读 thread；同一任务用两个 agent 并行跑，比较结果。

## 4. 非目标（v1 明确不做）

- 不自建 agent runtime、不做模型路由、不做 prompt 编排框架。
- 不做云端代码执行沙箱。agent 在用户自己的机器上跑。
- 不做代码托管。远端仍然是 GitHub、GitLab 或自建 git。
- 不做 IDE。编辑器、终端、调试器不是本期目标。
- 不做企业级能力：SSO、SCIM、合规审计导出、按席位计费。
- 不做移动端专用客户端。浏览器响应式能看即可。

## 5. 核心概念与领域模型

| 概念 | 定义 | 关键约束 |
| --- | --- | --- |
| Project | 本地一个目录，通常是一个 git 仓库，可绑定一个 remote | 同一 project 在所有视图中作为一级导航；路径必须是绝对路径且经用户确认 |
| Thread | 一次可共享的 agent 工作过程，包含消息、工具调用、计划、变更和评论 | thread 是权限和分享的最小单位；未分享时仅本地可见 |
| Worktree | thread 的隔离工作区，默认从 project 的某个基线创建 git worktree | 一条 thread 最多一个主 worktree；worktree 目录由产品管理，不放进 project 内 |
| Turn | 一次用户输入到 agent 停止的完整过程 | 一条 thread 同一时刻最多一个进行中的 turn |
| DraftBlock | 一条带作者的草稿块，多人共享的输入区由若干块按顺序组成 | 块内文本用 CRDT 合并；发送时由服务端事务合并末尾连续块 |
| Event | thread 内有序、不可变的事实记录 | 每条 event 带单调递增 `seq`；客户端按 `seq` 重放 |
| Participant | 参与 thread 的人或 agent | 人分 owner、editor、viewer 三种角色；agent 有唯一 binding |
| AgentBinding | 一条 thread 与某个 agent 会话的绑定关系 | 记录 agent 种类、会话 id、工作目录、模型与配置项；会话 id 只是恢复句柄，不是历史真相 |
| PermissionRequest | agent 发起的审批请求 | 必须显式处理；默认拒绝；处理结果写入事件日志 |
| Comment | 挂在消息、文件或 diff 行上的评论 | 支持回复和已解决状态；评论不改变代码 |
| ChangeSet | 一条 thread 从基线到当前的累计变更 | 可按 turn 或按文件查看；未提交变更与对话在同一屏 |

关系：一个 Project 有多个 Thread；一个 Thread 有一个 Worktree、一个 AgentBinding、多个 Turn、多个 Participant 和一条 Event 流。

## 6. 关键流程

### F1 添加并打开 project

用户选择一个本地目录，产品校验是否为 git 仓库、是否有 remote、当前分支是什么，然后登记为 project。列表展示 project 名、路径、活跃 thread 数、最近活动时间。

验收：添加非 git 目录时给出可理解的提示；同一路径不能重复添加；路径失效时列表项标记为「不可用」而不是崩溃。

### F2 新建 thread

用户在一个 project 下新建 thread，选择 agent、模型、起始分支。产品创建 worktree，启动 agent 进程，建立会话绑定，然后进入对话界面。

验收：从点击「新建」到可以输入第一条消息不超过 3 秒（agent 启动时间另计，需要显示启动进度）；worktree 创建失败时清理残留并报错。

### F3 对话与工具调用

消息流式输出，工具调用以可折叠卡片展示（读文件、改文件、执行命令、搜索、MCP 调用等）。改文件的工具调用要能直接看到 diff 摘要，点击展开完整 diff。计划（plan）、推理摘要、上下文用量按 agent 是否提供来展示，缺失时不占位。

验收：首字延迟不高于 agent 本身输出延迟加 200 毫秒；工具卡片在 turn 结束后仍可展开；同一工具调用的多次更新合并为一张卡片，不重复插入。

### F4 审批

agent 请求权限时，生成一条待审批项，进入 thread 内联区和全局收件箱。审批项包含：要做什么、涉及哪些文件或命令、完整参数、可选操作（本次允许、本会话允许、本 thread 一律允许、拒绝并说明原因）。

验收：审批请求在 1 秒内出现在所有正在观看该 thread 的客户端；处理结果对被拒绝的工具调用产生可读的反馈；「一律允许」有明确的生效范围和撤销入口。

### F5 分享与加入

owner 可以生成分享链接，选择访问级别：仅邀请、团队成员、持链接可看。被邀请者打开链接加入 thread，按角色获得读或写权限。

验收：viewer 无法发送消息或审批；链接泄露后的撤销立即生效；未登录用户看到的是登录页而不是空白页。

### F6 多人实时

同一条 thread 的所有参与者看到同一份消息序列、草稿块和变更。界面显示在场成员、谁正在输入、agent 是否正在运行。

验收：两人同时打开同一 thread，任一方发送消息，另一方在 1 秒内看到；网络断开重连后不重复、不丢消息；并发发送时按服务端顺序落库并回显。

### F7 变更审阅

右侧 Changes 面板列出文件和增删行数，可按四种基线比较：基线分支、Last Commit、Last Turn、某个 commit。逐文件、逐 hunk 查看；每文件可标记 `Seen`，头部显示 `3/17` 进度；提供把变更合回 project 主工作区的操作，默认不自动提交。

验收：变更视图与磁盘实际内容一致；外部编辑器改动后能刷新；`Seen` 是个人状态，文件再次变更时自动清除；不提供 per-hunk keep/undo，改为整体回滚（`Revert Conversation to Cursor`）与按基线对比；评论锚点在文件变化后不静默错位，无法定位时降级为文件级评论。

### F8 断线与恢复

浏览器关闭或断网后重连，按 `seq` 补齐事件；本地服务重启后，thread 仍可打开，agent 会话尝试恢复；恢复失败时明确告知上下文已重置，并提供继续对话的方式。

验收：断线 30 分钟内重连不丢事件；服务重启后 thread 列表和最近消息完整；agent 进程异常退出时 thread 标记为「已中断」而不是卡在运行中。

### F9 Thread 生命周期

支持重命名、归档、复制（fork 出新 thread 和新 worktree）、删除。归档后默认不出现在活跃列表，历史可查。

验收：删除 thread 必须二次确认，并说明 worktree 与未提交变更的处理方式；fork 后原 thread 不受影响。

### F10 Project 概览

project 首页展示：进行中的 thread、等待审批的项、待评审的变更、最近活动。目标是一屏看清「这个项目现在在发生什么」。

验收：从概览可以一次点击进入对应 thread 的具体位置；没有数据时区分「还没有 thread」和「加载失败」。

### F11 焦点共享与跟随

在场成员共享自己的语义焦点：当前 project、thread、面板、文件、行号或 diff hunk、消息位置。其他成员可以看到每个人的光标标记、头像和颜色，并可一键「跟随」某人，视图随其焦点移动。

验收：

- 焦点变化到其他人看到不超过 300 毫秒，且不产生持久化记录。
- 跟随状态下，被跟随者切换 thread 或文件时，跟随者自动跳转，并显示「正在跟随 X」的顶部提示与退出按钮。
- 跟随者自己输入、滚动或点击时自动退出跟随。
- 被跟随者离线超过 30 秒，跟随自动结束并提示。
- 焦点以语义锚点描述（thread、文件、行、hunk、消息 id），不依赖像素坐标，不同窗口尺寸下都能正确落点。
- 每个成员可关闭焦点共享（隐身），关闭后其他人看不到其光标。

草稿块内部的字符级光标不做实时同步；界面上的光标与跟随只覆盖语义焦点。需要「看到对方正在改哪条草稿」时，用块级状态表达。

### F12 子 agent 展示

agent 派生子 agent 时，主时间线里的派遣调用变成可展开的卡片；左栏本身就是 Delta 风格的树：Project → Thread → Subthread，带 chevron 可展开、可嵌套。不设右侧花名册。

验收：

- 同时 3 个子 agent 时，树中有 3 个节点并带状态；批准其中一个不阻塞其余，界面明示「其余仍在运行」。
- 父节点默认展开最新 10 个子 thread，底部显示 `Show N more`；`⌘/Ctrl + J` 可打开全量选择器。
- 嵌套两层时缩进与面包屑正确，子事件不在父层重复出现。
- 子 agent 崩溃时节点显示错误与停止原因，父 thread 仍可继续。
- 断线重连后树与状态从快照恢复，子会话 transcript 按需加载。
- agent 不支持子会话时不崩溃、不出现空节点，退化为工具调用卡片并标注「无独立会话」。
- 子会话视图不提供输入框，只能取消（若 agent 声明支持）或回到父 thread 发言，并给出「让父 agent 转达」的模板。
- agent 之间的消息折叠为 `Sent Agent Message` / `Received Agent Message`，可展开。

### F13 提问与回答

agent 需要用户确认或补充信息时（elicitation），以卡片形式出现在时间线，同时进入收件箱。表单支持修改后提交，动作为提交、拒绝、取消三种。

验收：

- 卡片不阻塞阅读；同时多个提问不堆叠成多个模态框。
- 表单按钮与对 agent 的语义一一对应，不能把拒绝和取消合并。
- 多人同时在线时只接受第一个有效回答，其余客户端立即变为只读并显示回答人。
- 回答写入事件日志与审计；提问因 turn 取消而失效时自动消失并留痕迹。
- 需要外部授权时显示完整 URL 与主机名，显式同意后才在新标签页打开。

### F14 队列与中途插话

用户可以在 agent 运行中继续表达：支持 steering 的 agent 直接并入当前 turn，不支持或当前不可接收时进入 thread 级队列，turn 结束后按序发送。

验收：

- turn 中连续发 3 条，队列按序执行，界面显示每条的位置，可撤回。
- 支持 steering 时显示「已并入」；返回不可接收时自动转入队列，不丢失输入。
- 队列属于 thread，刷新页面或换设备后仍存在。
- turn 被取消时队列保留，每条标记「上一轮已取消」，由任一 editor 决定继续或清空。
- 其他成员的输入按同一套投递规则处理：插话、停止并发送或排队，由发送者选择。

### F15 评论与标注

成员可以在消息、工具调用、提问、文件行和 diff hunk 上留下评论与回复。评论默认处于 pending，随下一条消息一起提交给 agent，也可单独提交；agent 的回复与评论双向链接。

验收：

- 选中文本直接输入即创建 draft 评论，不切换模式；`⌘/Ctrl + Option/Alt + M` 同效。
- 评论以边栏或行内边距呈现，不修改 agent 消息本身。
- pending 评论随下一条消息一起送达；单独提交不带消息也能送达。
- agent 回复与评论双向可跳转；流式期间评论回复跟随回答展示。
- diff 行锚点在文件变化后能降级为文件级评论，并标注「原位置已变化」。
- 文件/diff 评论提交后折叠为 gutter 标记，可一键重新打开讨论。
- 评论不触发 agent；@提及产生通知。

## 7. 多人协作语义

多人共享一条 agent 会话，必须先把规则写死，否则实现阶段会互相矛盾。

- **发言权**：editor 及以上都可以直接发送、插话、停止并发送，没有 driver，也没有「接管」按钮；不做建议队列。owner 可以把 thread 设为「仅 owner 可发送」。
- **草稿块**：每人一块，块带作者；任何人可以编辑任何人的草稿，块内字符级 CRDT 合并；草稿对所有参与者可见，可以在里面聊天。没人点发送，agent 收不到。
- **发送**：把末尾连续草稿按作者顺序合并成一条消息，保留作者列表，turn 与用量记在发送者头上。两人同时发送时服务端只接受第一个，第二个按插话 / 停止并发送 / 排队处理。
- **接管**：没有显式接管。打开同一条 thread 直接发言即可；agent 看到每条消息的作者。
- **焦点**：成员的当前 thread、文件、行、hunk 属于易失状态，只走 presence 通道，不落库、不重放、不参与权限判断。隐身成员的焦点不下发。
- **子 agent**：子会话只读，不能向它发 prompt；其审批只阻塞自身，不阻塞主 turn；子会话工作目录与 thread 根目录不同时，审批项必须显示目录，且不继承「一律允许」。
- **提问**：任何 editor 都可以回答，服务端只接受第一个有效响应；回答人与时间写审计。
- **队列**：队列属于 thread，由服务端持有；中途输入优先插话（steering），其次停止并发送，最后才是排队。排队可撤回，不因刷新或换设备丢失。
- **评论**：不触发 agent，不改变 thread 状态。pending 评论随下一条消息提交；单独提交不带消息也能送达。
- **离开与闲置**：无人观看超过一定时间后 agent 进程可以回收，thread 保持可恢复状态。

## 8. 信息架构与界面要求

整体对齐 Delta v0.24.0 的三栏外壳，以 project 为一级维度。逐屏规格见 [05-ui-spec.md](05-ui-spec.md)。

```
┌───────────────────────────────────────────────────────────────┐
│ ▣  ⌕        thread 标题            ● ● ●   [分享] [审批] [▤]  │ 标题栏
├──────────────┬────────────────────────────────────────────────┤
│ Pinned       │ tab: Thread | Changes +12 −3 | Files           │
│  ├ thread    │ ┌────────────────────────────────────────────┐ │
│ Projects     │ │ 时间线（单列，头像列 56px）                  │ │
│  ├ project   │ │ 折叠摘要行 + 消息 + 工具卡 + 审批卡          │ │
│  │  ├ thread │ └────────────────────────────────────────────┘ │
│  │  │  └ sub │ composer（与时间线同宽）                       │
├──────────────┴────────────────────────────────────────────────┤
│ ⌘ project  branch ⌄        +694 −85      3 运行中 · 1 等待审批 │ 状态栏
└───────────────────────────────────────────────────────────────┘
```

要求：

- 标题栏：左侧侧栏开关与搜索；中间 thread 标题与参与者头像；右侧分享、审批、右栏开关。
- 底部状态栏：project、分支、`Work In` 选择、增删行数、运行中与等待审批计数。分支与 worktree 不放在头部。
- 左栏即树：`Pinned` / `Projects` / `Threads` 三个分组；project 下直接挂 thread，子 thread 缩进并带引导线；分组末尾 `Show N more`，默认 10。
- 时间线单列，密度由折叠摘要行控制（`Ran 3 commands, thought, read a file ›`），文本段落不折叠。
- 子 thread 用树 + tab，不用卡片网格；`⌘/Ctrl + J` 打开一级子级选择器。
- 右栏是抽屉，默认 Changes；`Shift+Esc` 关闭。
- 在场成员头像常驻标题栏；点头像可跟随，颜色按用户 id 稳定映射。
- Changes 用 `Seen` 复选框与 `3/17` 进度，不做 per-hunk keep/undo。
- 收件箱汇总审批、@提及与邀请；条目格式为「谁 @ 了你 + 相对时间 · thread 标题」。
- 空状态、加载、错误、断线、等待审批分别设计，见 05 文档第 13 节。

## 9. 功能清单

| 优先级 | 功能 | 说明 |
| --- | --- | --- |
| P0 | 添加 project、列出 thread | 产品的地基，必须以 project 为一级维度 |
| P0 | 新建 thread、worktree、启动 agent | 打通单个 agent 的完整闭环 |
| P0 | 流式消息与工具调用展示 | 含 diff 摘要与折叠 |
| P0 | 审批（内联 + 收件箱） | 默认拒绝，可撤销的一律允许 |
| P0 | 断线重连与事件重放 | 没有这个，多人共享不成立 |

## 10. 同步与部署形态

已定：**单机多用户**。一个服务进程跑在有代码的机器上，多人通过浏览器访问同一个页面；该机器离线则 thread 不可访问。

直接后果：

1. 必须有账号体系和 thread 级角色（owner / editor / viewer），不能只用一个访问令牌。
2. agent 凭据属于机器，不属于用户。所有参与者共用这台机器上的 agent 登录，界面必须固定展示当前 agent 身份与账号。
3. 事件日志只有一份权威副本，在服务端；客户端不做本地优先合并，也不做离线写入。
4. 不做 relay、不做多副本。草稿层用 CRDT（对齐 DeltaDB 的文本同步）；事件日志仍是服务端定序，不用 CRDT 合并。
5. 只允许 Tailscale 网络访问：服务绑 `127.0.0.1`，由 `tailscale serve` 终结 TLS 并转发；不暴露公网。

为什么不选其他形态：

| 形态 | 不选的原因 |
| --- | --- |
| 各自本地 + 中心 relay | 需要账号、云存储、权限与冲突设计，工作量约为单机的 3 到 5 倍；当前团队规模用不上 |
| 纯 P2P / CRDT 同步 | 排序与审批语义难保证，与「服务端唯一写者」冲突 |

## 11. 权限与安全

这是本地服务形态下最容易出事的部分，列为硬性要求。

- 服务固定监听 `127.0.0.1`。远程访问只通过 `tailscale serve` 转发，由 Tailscale 提供 TLS 与网络层访问控制；不支持端口转发或公网绑定。
- 所有写操作校验 Origin 与会话 Cookie，并要求自定义请求头；禁止通配 CORS。
- 账号密码用 `argon2id` 存储；会话可在服务端撤销。
- 文件读写限制在 project 根目录和 thread 的 worktree 根目录之内，同时做词法校验和真实路径校验。
- 审批默认拒绝。允许规则按 project、agent、工具、命令前缀限定范围，并能查看和撤销。
- 界面上必须明确提示：允许 agent 执行命令等价于在该机器上获得 shell 权限。
- agent 输出按不可信内容渲染，Markdown 与 HTML 必须清洗。
- 事件日志记录审批人、审批时间、审批结果和工具参数摘要。

## 12. 非功能需求

| 项 | 要求 |
| --- | --- |
| 重连 | 断线 30 分钟内可补齐事件；超出缓冲则全量重同步 |
| 崩溃恢复 | 服务重启后 thread 可打开；agent 会话恢复失败要显式降级 |
| 延迟 | 本地环境事件到界面渲染增量不超过 100 毫秒 |
| 容量 | 单 thread 10 万条事件仍可打开，首屏只加载最近窗口 |
| 跨平台 | macOS 与 Linux 优先，Windows 二期 |
| 可诊断 | thread 元数据记录 agent 名称、版本、协议版本、启动参数 |
| 可降级 | agent 未提供的能力（计划、用量、子 agent）不显示，不报错 |
| presence | 焦点更新端到端不超过 300 毫秒；客户端发送上限 10 Hz，服务端按 (thread, user) 合并；不落库、不重放 |
| 审批 | 不自动拒绝、不超时消失；无人处理时 thread 持续显示「等待审批」，直到有人处理或 turn 被取消 |

## 附录 A：agent 接入调研结论（2026-02）

结论：用 ACP v1 作为接入层，本地服务充当 ACP client，浏览器只与本地服务通信。

事实依据：

| 事项 | 结论 |
| --- | --- |
| 协议版本 | ACP v1 稳定，v2 仍是 experimental；TS SDK 默认导出 v1 |
| 传输 | 只有 stdio；HTTP 与 WebSocket 传输仍在 RFD 阶段，浏览器对接需要自建桥接 |
| Claude Code | `@agentclientprotocol/claude-agent-acp`，覆盖最全（工具、权限、计划、子 agent、终端、slash 命令） |
| Codex | `@agentclientprotocol/codex-acp`，内部通过 `codex app-server`（官方标注 experimental）翻译 |
| opencode | 原生 `opencode acp`，实测 `initialize` 返回 `protocolVersion: 1`，支持 session 的 list/fork/resume/delete |
| pi | 无原生 ACP，社区 `pi-acp` 适配器；pi 自身的 SDK 与 RPC 模式更完整 |
| 协议缺口 | 不做多客户端广播、不做持久化、不规定历史由谁持有；会话状态属于进程 |

推论：产品必须自己持有 thread 的事件日志，agent 会话 id 仅作为恢复句柄。这与第 5 节 AgentBinding 的定义一致。
